# Backend

The backend will be a fairly basic CRUD Typescript server. It will use Node.js as its runtime, Fastify as the HTTP framework, MikroORM as the database framework (https://mikro-orm.io/llms.txt), and tRPC as the API framework. The database should use SQLite. The API should be tested using Vitest. Things related to security and privacy should be thoroughly tested with `fetch` calls to simulate an attacker.

Use the latest (v7) recommended MikroORM entity declaration style (`defineEntity` with a class: https://mikro-orm.io/docs/defining-entities.md). Use the recommended serialization functionality (https://mikro-orm.io/docs/serializing.md). Do **not** create separate types for entities that are independent of the database types.

Types for API models should be built on MikroORM DTOs using TypeScript utility types like `Pick<>`. The API models should be based on what will be useful for operations, and the operations should be based on the common read/write operations for users: for example, listing all of the users' logbooks for the splash screen or all of the entries in a logbook for the organizational view (which should not involve downloading all of the data for those entities). The API types should be in the backend package, and the frontend should import them from the backend package.

Again, the available API operations should be based on the reads and writes of user flows that are exposed by the frontend; for example, if the frontend allows several entries to be rearranged in one step, it should not have to make multiple API calls to change the positions of each of those entries; instead, it should be able to make a single API call to bulk update the positions of all of those entries at once.

All API calls should be validated for both type safety and logical validity. For example, a bulk position update should not be allowed to assign the same position to multiple entries.

All API routes should be prefixed with `/api`.

## Content

The backend may need to inspect or process the content produced by the editor on the frontend. However, the backend should not depend directly on the frontend rich text editor framework. Instead, a separate package called `content` should provide an interface that abstracts away the details of the rich text content that the editor produces. (Transitively depending on the editor framework is fine; the point is just that if the editor changes, the actual code in the backend does not change.) It should contain the tools to handle things like word counts or serialization. It should not contain anything related to the app's actual view layer (i.e. React.) This can be accomplished by defining a things like `DecoratorNode`-based classes to create custom content types in the `content` package, and then extending them to add view layer functionality in the frontend code.

### Images

It should be possible to upload images for use in the content for an entry. JPEGs, PNGs, GIFs, and WEBPs should be supported. The maximum image size should be 10 MB. Images should be uploaded using multipart form data, using tRPC's `zod-form-data` integration, as in [this example](https://github.com/trpc/examples-next-formdata/). (That example uses Next.js, but the same basic pattern can be used with Fastify.) The form data should contain the image file, its original file name, the ID of the entry it's being inserted into, and the ID of the logbook that contains that entry. It needs to have an Authorization header that proves that the user has permission to edit that logbook. (The logbook ID is included in the form data so the Authorization header can be quickly created and checked; the server should still independently confirm that the entry actually belongs to the authorized logbook.) The npm package `image-meta` should be used to detect and enforce the specified file types.

Images should be recorded in a database table that stores the image's random ID, its MIME type, its width and height (which should also detected with `image-meta`), the timestamp of its creation, its original filename, a URL-safe version of its original filename (falling back to just `image` if there is no usable original filename somehow), and the ID of the entry that it was uploaded for (which is a foreign key that should be `set null` if the entry is deleted). (Note: since images can be copied and pasted and thus shared between different entries, an image may end up being referenced by one or more other entries; an image only has to be attributed to an entry when it's uploaded to keep it from being too easy to upload and park random images on this server.)

There should then be a backend route that serves the images under the path `/api/images/[id]/[url-safe version of original filename]` with appropriate cache control headers, plus `X-Content-Type-Options: nosniff` (just in case there's a possible file that would get detected as one format by `image-meta` and a different one by a browser.) When an image is uploaded via a HTTP request, the server needs to respond with the newly-created image database row, so the frontend can then add a reference to the image to the entry's content in the appropriate place.

Pasting HTML copied from a web page brings `<img>` elements that point at other origins. The frontend code can't necessarily fetch those images to upload them to the backend, due to the same-origin policy, so there needs to be a dedicated procedure for retrieving an image that lives at an external public URL and storing it just like an image that was uploaded from the end user's computer. Note that this logic should be carefully guarded to ensure it can't become a SSRF or exfiltration vector (it should only try to load images served with http or https on domains that resolve to IP addresses that don't fall into the ranges used by private networks.)

The implementation details of image storage should be hidden by a singleton service class called `ImageBox`. The initial implementation will just store images in local files, divided into two levels of directories by the first characters of their IDs. (This directory structure exists to ward off a scenario where one directory contains enough items to cause file system performance issues.) Image IDs are restricted to lowercase alphanumeric characters so that this path layout stays stable on case-insensitive file systems, where two IDs differing only in case would otherwise collide on disk. `ImageBox` should handle the logic of storing images that are uploaded and retrieving them when they're served by the images route in such a way that its implementation can later be switched out for something else (like bucket-based object storage) without disrupting any other code.
